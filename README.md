# 工业网关（STM32F407 + FreeRTOS + LVGL）

RS485 温湿度采集 → 本地存储 → 云端上报 → OTA 升级的一体化网关。
带 3.2 寸触摸屏，采集、链路、存储状态全部上屏，支持断网补传与固件回滚。

## 功能

- **采集**：Modbus RTU 主站，RS485 挂 HZ8706 温湿度变送器（地址 1 / 9600 8N1）
- **显示**：LVGL 9.5 四页界面（首页 / 设置 / 关于 / 事件），滑动或 KEY2 翻页；屏上可扫描并输入 WiFi 凭据
- **事件日志**：上电/断网/对时/参数变更/OTA/告警等落盘到独立环形区，屏上第 4 页可翻查，断电留痕
- **存储**：W25Q128 上 3MB 日志区，按 4KB 扇区顺序追加；已发记录只改一个字节标记，写满且全部发完后自动回绕
- **上报**：ESP-01S AT 透传 + 手写 MQTT 3.1.1（CONNECT / PUBLISH / PINGREQ），连巴法云
- **下行**：订阅同一主题，云端 PUBLISH 过来的命令实时生效：周期、告警阈值、远程重启、恢复出厂
- **告警**：温湿度各设上下限，越限时屏上大数字变红；上报带 `alm` 状态位与 `ev` 事件位（开始/提醒/恢复）
- **补传**：断网期间数据留在 Flash，重连后按 200ms 间隔限速追平，避免灌满 ESP 串口缓冲
- **时间**：LSE + VBAT 的 RTC，联网后 UDP 直发 NTP 校时；未校准时界面显示 `--:--`，不显示假时间
- **看门狗**：IWDG 心跳门控——五个任务都推进过才喂狗，任一任务停滞则停止喂狗，约 50 秒内自动复位；
  且开机最早期就启动，启动阶段卡死同样 30 秒自动复位（不会永远停在上电自检页）
- **OTA**：屏上弹窗显示下载进度，bootloader 独立工程，坏固件按 try 计数自动回滚；
  黄金备份**需人工固化**（`{"golden":1}`），避免"能开机但一操作就死"的固件顶掉真正可用的备份

## 数据链路

```
485 采集 → uart_poll_task → sample_task ─┬→ UI（最新值）
                                        ├→ 队列 → Flash 日志区（环形，带 seq/ts）
                                        └→ MQTT 上报（失败留库，重连补传）
```

上报报文：

```json
{"ts":1794288672,"temp":20.1,"humi":41.7,"seq":2163}
```

`ts` 为 UTC Unix 秒（RTC 校准后为真实时间）；`seq` 单调递增，重启不归零。

## Flash 分区与升级

| 区域 | 位置 | 用途 |
|---|---|---|
| Bootloader | 内部 Flash `0x08000000` | 校验、安装、回滚 |
| APP | 内部 Flash `0x08010000` ~ `0x08100000` | 运行区 |
| 暂存区 | 外部 Flash | OTA 下载落点，装完即校验 |
| 黄金备份 | 外部 Flash | 人工固化过的固件（回滚目标） |

升级流程：APP 从服务器拉固件写入暂存区并校验 CRC32 → 复位 → boot 校验暂存区 → 安装进 APP 区 → 跳转新固件。
若新固件起不来，boot 按 try 计数重试，达到阈值后从黄金备份回滚（连续 4 次启动失败触发）。

**黄金备份不在 OTA 时自动写入。** 只有确认这一版在现场跑稳了，才发 `{"golden":1}` 把当前固件固化成备份。
原因：能开机不等于够可靠——"能亮屏、按某个键才崩"的固件同样能通过启动确认，自动搬会把上一份真正好用的备份顶掉。
固化约 20~30 秒，顺序是"先作废旧备份 → 擦写 → 回读校验 → 才记长度/CRC"，中途掉电最坏只是没有备份，不会留下假备份。

首发/出厂时请固化一次：不然回滚时 boot 只能打 `no golden, halt` 停机等人。

## OTA 升级

```bash
python tools/ota_server.py --bin gwbase/Obj/gwbase.bin --version 1.0
```

服务器监听 `0.0.0.0:8888`，板上按 KEY1 触发升级，屏上弹窗显示进度与结果。

## 云端改参数

板子订阅上报用的同一主题，在该主题下发 JSON 即可在线调整，键可选：

```json
{"mb":5000}
{"pub":3000}
{"mb":5000,"pub":10000}
```

| 键 | 含义 | 范围 | 默认 |
|---|---|---|---|
| `mb` | 485 轮询周期（ms） | 500 ~ 60000 | 2000 |
| `pub` | MQTT 上报周期（ms） | 1000 ~ 20000 | 2000 |
| `tmin` / `tmax` | 温度告警下限 / 上限（℃） | -40 ~ 80 | -40 / 80 |
| `hmin` / `hmax` | 湿度告警下限 / 上限（%） | 0 ~ 100 | 0 / 100 |
| `alarm` | 告警判定开关，下发任一阈值会自动置 1 | 0 / 1 | 0 |
| `reboot` | 远程重启，值必须为 `1` | — | — |
| `reset` | 恢复出厂参数并重启，值必须为 `1` | — | — |
| `golden` | 把当前固件固化成黄金备份（回滚目标），值必须为 `1`，耗时 20~30 秒 | — | — |

生效后串口打 `[cmd] mb=5000 ... applied`。**参数写入外部 Flash 的两个 4KB 扇区（A/B 轮换 + CRC），断电保留。**

阈值命令会做上下限校验：`tmin >= tmax` 或 `hmin >= hmax` 时**整条命令拒收**（串口打 `[cmd] bad range`），
不会写进半套配置 —— 配反了会让告警恒亮，现场很容易误判成传感器坏了。

`pub` 的上限压在 20 秒不是随手取的：板子只在每轮上报结束时才发 MQTT 心跳（PINGREQ），
上报周期有多长，心跳间隔就至少有多长；而 broker 按 1.5×keepalive（30 秒）判死链路。
放到一小时的话，链路必然在半路被踢，设备会陷进"连上 → 睡一小时 → 掉线 → 重连"的循环。

`golden` 与前两组不同：它不改参数，而是把**当前正在跑的这份固件**写进黄金区。OTA 装完不会自动写，
确认这一版跑稳了再发一次即可。下发后屏上会弹出和 OTA 同款的进度窗口
（准备 → 擦除 → 搬运 → 校验 → 完成），约 20~30 秒，结束后自动关闭。

关于页最后一行显示备份状态：`560KB 11-11 19:35` 是大小与固化时刻；末尾带 **`旧`** 并标黄，
说明这份备份不是当前正在跑的固件（OTA 之后没重新固化），此时回滚回去的是旧版本。

上报报文：

```json
{"ts":1794313869,"temp":22.5,"humi":41.4,"seq":3431,"alm":0,"ev":0}
```

`alm` 是这条数据本身的越限状态；`ev` 只在事件发生的那一条上非 0（1=告警开始、2=持续提醒每 5 分钟、3=已恢复），云端按 `ev` 过滤即可得到事件流。

## 已知限制

- 未校准的时间在补传时仍是编译时刻兜底值，云端可能收到异常时间点
- 无纽扣电池时，每次断电都会回到编译时刻，需联网重新校准
- OTA 传输偶发握手后 0 块断开，板子会自动重连重试，通常第二次成功
- 日志区写满且有未发数据时会停止记录（防止覆盖没传上去的数据），屏上关于页显示 `FULL 停记`
- 启动阶段卡死会变成"每 30 秒复位一次"的循环而不是静止停机；若是 ST-Link 烧录的固件（不经过 OTA 的 try 计数），这个循环会一直持续到有人重烧
